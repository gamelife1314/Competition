### 1.2 结论：失血的结构性分布

1. **score1（任务分）是当前最大、最稳定、最可修复的失血管。** 最近四场有分项证据的对局，任务差距为 -139、-240、-345、约 -80——issue #21 明确指出"任务 0 分 vs 对手 240 分（-240）"而击杀 105 持平；issue #23 对手 139 分**全部**来自两个任务（91+48），我方 52 分里 0 任务分。我方自 pk574078 起**全赛季任务成功次数为 0**（最好成绩：#12 北京任务间接得 16 分、#13 alpha 任务 +86 分——是仅有的两次非零）。
2. **score2 已从"最大短板"变为"偶发亮点"，但受三座塔与哑火率钳制。** 早期 -62（#3）的根因（夜间无人操炮）已修；pk577297 我方 2 塔打出 kill=105 并拆毁敌基地。但只要第三塔缺席（连续 5+ 场，见 §5.1）且夜间哑火（`controller_withdrawn` 30+ 次，#22/#23）存在，清怪速度就上不去，D2 夜后墙环被磨穿只是时间问题（#19：D2 夜 1500→105）。
3. **score3 的 D1 猝死已被墙环治愈，D2–D4 慢死成为主形态。** D1 闭合墙环自 #19 起稳定（13–20 墙、13000–20000 HP、D1 基地零失血）。但破口重开（#21：17→7；#23：19→13）+ 无钱修墙 + 控制器带伤撤退形成死亡螺旋，基地在 D2–D4 夜被磨死（#18/#19/#20/#23），每提前一天死亡损失 90～100 生存分；与满生存 550 的理论差距仍在 450+。
4. **三项的耦合点：金币。** 任务 0 分 → 无任务金币（对手单任务 +80 金）→ 买不起券/药/修墙包 → 塔少、哑火、墙修不动 → score2/score3 同步受损。任务系统不只是 score1，它是整个经济的第二发动机。

**收益排序：score1（任务）≫ score3（D2+ 生存）＞ score2（第三塔/哑火）。** 理由：score1 差距 139–345 分/场且不依赖对手失误；score3 修复依赖经济与防御协同，周期更长；score2 在 2 塔满操时已基本持平。

### 2.1 完整失败链诊断（逐环定责）

链路：发现 → 接取 → 路径假设 → LLM 构造 → 沙盒执行 → 答案提取 → schema 校验 → 提交 → 成功判定。

| 成功判定 | 三信号闭合（state.rs:560–593） | #15 提交漂移已由 `task_answer_submit` 日志闭合 | ✅ 已修 |

**失败链的根因（不是症状）：**

1. **schema 双目失明**：判分依据的字段schema 只存在于两处——沙盒内的任务文件（API_DOCS.md / task_X.md 正文）与判题器的拒绝描述。我方当前的 `expected_fields` 解析的是 `phaseTask` 占位描述，从信息论上就不可能猜对；而唯一权威反馈 `errors[].description` 在解析层被丢弃。这不是"LLM 不够聪明"——#20 起脚本能跑、`ANSWER:` 能提取，LLM 是在**完全没有反馈**的情况下盲改。对手的全部优势（#10/#14）就是把这个反馈环闭上了。
2. **accept 不看可赢性**：`next_task_point` 对 `timeoutRounds` 不做筛选。超时预算小于管道延迟（4–5 回合）的任务在接取瞬间就是死局，还烧掉该点 30 回合冷却，并把先锋钉在点上（#20/#22 偶数 session 全灭）。
3. **重试预算与信息量错配**：盲改时代 3 次放弃是合理的（#15 教训：对手失败后立即放弃转防御）；但在有 description 反馈后，每次拒绝都带来新 schema 信息，放弃阈值应随"是否获得新信息"而非固定次数。

### 2.3 具体改造方案（按依赖排序）

**T1（P0，一切的前提）：打通 `errors[].description` 反馈环。**
- `model.rs`：`Turn` 增加 `error_descriptions: Vec<String>`（与 `error_codes` 平行），不再丢弃。
- `state.rs::absorb_llm_and_cmd`：提交后收到 errorCode 2 时，把 description 存入 `task.rejection_feedback: Vec<String>`（保留全部历史，去重）。
- `task.rs::build_prompt`：把拒绝描述原文注入重试 prompt（"判题器原话：……"），并指示 LLM 按描述增/删/改字段。
- `log.rs`/`mod.rs`：`task_answer_rejected` 事件记录 description 全文——同时填补证据缺口（§0.2.2），让下一场就能验证 description 里到底有没有字段名。
- 风险：极低（纯增量）。若 description 为空/无信息，行为退化为现状。

**T2（P0）：accept 可赢性门槛。**
- `day.rs::next_task_point`：接取前估算管道延迟 `pipeline = 4`（无 SOP 命中）/ `1`（有 SOP 命中且模板可绑定）；仅当 `timeoutRounds > pipeline + 2` 才接取。不满足但有 SOP 命中的，直接走 SOP 快速路径（task.rs:160 已支持首回合发命令）。
- 不退役该点（与 `cmdRounds=0` 的死点退役区分：可赢性不足是"暂不接"，不是"点已死"），先锋转去防御/寻宝。
- 收益：消除偶数 session 的 `cmdRounds=0` 全灭（#20/#22/#23 共 10+ 个空烧 session），每个省下的都是 30 回合冷却与先锋时间。

**T3（P1）：沙盒内 schema 发现，取代描述猜测。**
- prompt 增加一条 SOP：第一步脚本必须 `cat` 任务文件与 API 文档，并把"任务要求输出的字段名/格式"以 `SCHEMA: {...}` 行打印出来；`on_cmd_result` 解析并缓存 `task.discovered_schema`。
- `HaveAnswer` 的校验从 `expected_fields(描述)` 切换为 `discovered_schema`（有则用，无则退回现状）；`answer_schema_gaps/extras` 的输入同步切换。
- `submittable_answer` 的单字段拆包启发式（task.rs:436）改为以 discovered_schema 为准：schema 是裸值就拆，schema 是对象就保留——#15 的 `{"token":...}` vs 裸值问题由真实 schema 裁决，不再靠"描述里是否提到该字段名"猜。

**T4（P1）：重试策略改为信息驱动。**
- `state.rs`：`MAX_WRONG_ANSWERS` 不再一刀切。每次拒绝带来**新的**（未见过的）rejection description 时重置计数；连续两次相同描述（= 没有新信息）才放弃。上限取 `timeout_round - 2`。
- 与 #15 教训的兼容性见 §7。

**T5（P1）：SOP 2.0——从"缓存脚本"到"缓存流程"。**
- 现 `SopEntry` 缓存单条命令（state.rs:113）。对手的成功模式是两段式：**探索脚本（读文档→打印 SCHEMA）→ 作答脚本（按 schema 构造 ANSWER）**。把 SopEntry 扩展为 `{explore_template, answer_template, schema}` 三元组，`find_sop` 命中后先跑探索（1 回合）再跑作答（1 回合），总延迟 2–3 回合，可赢 `timeoutRounds ≥ 5` 的任务。
- 保留现有防呆：指纹匹配（overlap≥3 且≥半数关键词）、参数绑定失败即弃用（state.rs:708/125）、答错即清该类型缓存（`drop_sop_for`）。

**T6（P2）：任务金币进防御预算。**
- 任务完成后 `goldReward×通过率` 到账；`economy.rs::intent_list` 不需要改动即可消费，但应在 `log_round` 的 `scoreAttr.residual` 之外单独记 `task_gold_earned`，验证正循环是否形成（对照 #10 对手 R76 后的采购链）。

## 3. 生存与防御策略升级

### 3.1 基地为何 D1–D3 夜反复被拆——防线的四个串联断点

1. **D1 猝死阶段（#3–#15）已治愈**：无墙 → 双格缺口 → D1 闭合墙环（#19 起稳定：R56–R60 封口、13–20 墙）。这是 `bb5cd6a`/`6c672f2`+`wall_daily_cap(D1=20)` 的功劳，必须保留。
2. **破口重开阶段（当前主战场，#18–#23）**：机器人整夜磨墙（#21：17→7 道、基地 1500→20；#23：19→13、基地 1165→45）。修复侧有三道闸：每日预算（`wall_daily_cap`，破口后已放宽到 20，#23 验证 R201 修复 18→19 生效）、石料采集（占住一个工人全天）、WallFixer（10 金回满一墙，**但金币冻结买不起**）。三道闸里最宽的那道（预算）已开，最窄的两道（石料人力、金币）卡死——修复速度 < 破坏速度。
3. **控制器撤退哑火阶段（#20 引入、#22/#23 恶化）**：`night_withdraw`（night.rs:522）把 <30% HP 且无药的控制器撤下炮位——保住了人，哑了炮。#22：20012 以 20 HP 冻结 235 回合，`controller_withdrawn` 触发 35 次塔全程沉默；#23：30 次。撤退后**没有任何恢复路径**能把它拉回岗位：游戏里唯一的回血手段是 Medicine（10 金），而 `self_provision`（day.rs:999）在金币 5 时返回 None。**撤退是对的，没有药的经济让撤退等于永久退役。**
4. **火力不足贯穿始终**：第三塔连续 5+ 场缺席（§5.1）。2 塔对 D2+ 的怪潮清怪速度不够（#18：361 回合总伤害仅 4930），漏怪 → 磨墙 → 破口 → 撤退 → 更少的炮 → 基地失血。四个断点互为因果。

### 3.2 协同问题：墙环/修复/塔位/控制器召回的相互作用

- **撤退判定只看"我站的地方危不危险"，不看"撤去的地方安不安全"。** `withdrawing`（night.rs:28）只检查机器人是否在当前位置 3 格内；当墙环被突破、机器人已进入内环时，`shelter` 的目标格（贴基地一圈）同样在机器人嘴边——撤与不撤都是死，而撤退还额外赔上一门炮的输出。
- **撤退判定不看"这门炮有没有替手"。** 3 人 2 塔时，带伤者撤退后 `stable_pairs` 会把炮给空闲者——但若三人全部带伤（破口后的常态），配对回退到"最近者"，然后该最近者又被 `night_withdraw` 拉走：炮在配对表上有主、在战场上无声（`night_debug` 里就是 30 次 `controller_withdrawn`）。
- **修复人力与经济人力互斥**：破口日非经济工人全天采石修墙（正确），经济工人独木支撑收入（#22 中它恰好又是那个 20 HP 的伤员），收入断 → 药与修墙包断 → 破口更大。
- **WallFixer 优先级设计正确但无钱执行**：`intent_list` 把半血墙列为 critical（economy.rs:298），逻辑对；金 5 买不起，全链停摆。

### 3.3 更智能的防御策略（非参数微调）

**D1（P0）：撤退的"可行性测试"与"替手测试"。**
- `night.rs::night_withdraw` 增加两个前置条件：① 安全测试——仅当存在一个 3 格内无机器人的 `interior_cells` 目标格时才允许撤；机器人已进内环时，贴基地与站炮位同样危险，此时**应原地开火**（炮的 DPS 是消灭威胁本身的唯一手段，撤退只是把死亡延后两回合且净亏一门炮的输出）。② 替手测试——若该塔无其他可配对的健康控制器且本控制器是当前唯一火力，权重向"带药坚守/无药坚守"倾斜；撤离只在没有火力代价时发生。
- 与 #20 修复的关系见 §7（不是回退）。

**D2（P0）：第三塔火力（方案见 §4.2，这是防御升级的最大单项）。** 3 塔 = +50% 清怪 DPS，直接压低磨墙时间，是破口问题的上游解。

**D3（P1）：把"杀啃墙者"提为夜间第一优先。**
- `combat.rs::threat` 已对贴墙机器人 +15，但 `win_value` 中击杀分（`kill_bonus_per_score=20×score`）仍主导排序，小型啃墙怪（1 分）排在远处的中型怪（2 分）之后。一只贴墙小怪每回合磨 1000 墙 HP ≈ 10 金修墙包 + 破口风险。建议：贴墙且 targetTeam=我方 的机器人在 `win_value` 中乘以固定倍数（如 ×3），让"保住墙"压倒"多拿 1 击杀分"。用 `CG_TUNE_*` 调参框架（combat.rs:43）做成可调，A/B 验证。

**D4（P1）：夜间道具的主动性使用。**

**D5（P1）：受威胁墙的重点加固。**

## 4. 经济与建造死锁

### 4.1 金币为何长期冻结在 5–25

冻结不是单一 bug，是**五条收入/支出规则叠加出的稳态**：

1. **D1 零收入是设计使然**：`shared_wall_duty`（day.rs:213）让 D1 双工人全天采石建墙，石头在墙需求未满足时不可卖（`sellable_ores`），D1 结束时的金币就是 75 减去建造与采购的余额。#22 的账目：75 − 50（两塔）− 20（Medicine×2）= 5，R4 起冻结。
2. **单一收入通道**：D2 起只有 `economy_id` 一个工人跑 collect→sell→buy；另一个工人在破口日全天采石修墙。这名独苗一旦受伤（#22 的 20012，20 HP）、阵亡或陷入路径震荡，全队收入归零。
3. **震荡通勤（561640b 刚修、未验证）**：`buyer_must_preposition` 此前把石头计入 `liquid_gold` → 判定"买得起 100 金券" → 买家（= 经济工人）空跑商店驻守 44 回合，采不了矿也卖不了货（#22 诊断原文）。修复把石头剔除出 liquid，方向正确，**但 pk577716（#23）跑的仍是旧码，冻结依旧**。
4. **矿—贩—店三角通勤**：矿点、小贩、武器商店是三个不同地点。经济工人按"采 4 个→走去卖→走回矿"循环，单趟 8–20 回合；`buyer_flow` 又可能在任何时候把它拽向商店。一个白天有效采集回合数被通勤吃掉大半（#8 旧版 513 回合仅 2 次 sell 的极端形态已消除，但 1–2 次 sell/天 仍是常态）。
5. **任务金币为零**：对手单任务 +80 金（#10），我方 0。第二发动机熄火，第一项（D1 零收入）的缺口无人填补。

### 4.2 第三塔为何建不起来——门槛体系的系统性失灵

`may_build_weapon`（economy.rs:543）在四道门后才有第三塔：

```
towers<2 → gold≥25 可建（D1 用掉 50 金）
towers=2 且无 L2 → 需 gold≥125（25 建塔 + 100 券储备）…… 门 A
              或 third_tower_fallback：gold≥25 且 day_round≥35 且 !upgrade_reachable …… 门 B
towers=2 且有 L2 → gold≥50 …… 门 C
```

- **门 A 永远够不着**：收入冻结时金币从未到过 125（#20：峰值 75→1；#22：75→5；#23：5–25）。
- **门 B 自相矛盾**：`upgrade_reachable`（economy.rs:578）用 `liquid_gold≥100`（**潜在财富**：背包里矿石的估值）判定升级可达；只要背包里有 ≥100 金的矿，fallback 就不触发——而矿石恰恰因为卖不出去才躺在背包里。**"潜在的富"同时堵死了第三塔和升级本身**：矿没变成钱 → 升级买不起 → `upgrade_reachable` 为真 → fallback 不触发 → 塔不建。#23 的 `tower_plan mayBuild=false（reserve=0）` 从 R3 贯穿全天，就是这个死锁的日志形态。
- **门 C 是先有鸡先有蛋**：若咬牙买了 100 金券，金币回落到 5，距 50 同样遥远。
- **对照组**：对手用初始 75 金 R1–R4 直接三塔（#20）、R1–R5 三塔（#9）、R6 三塔（#15）——**零储备策略**，把升级留给 D2+ 的收入。我方"先升级后三塔"的理论（#3 修复、AUDIT_PLAN P1）预设了一个从未兑现的收入水平；连续 5+ 场（#9/#15/#20/#22/#23）的实测证据全部站在对立面。

**方案（P0）**：
- D1 开门三塔：75 金 = gatling + railgun + rocket（25×3），墙环靠石头（免费），药与券靠 D1 黄昏前的首批卖矿（把 D1 的 `shared_wall_duty` 收窄：墙环缺口 ≤ 剩余预算半数时，经济工人即转 collect→sell，而非全天锁死）。
- 储备逻辑平移到 D2 起：`tower_build_reserve`/`may_build_weapon` 的三塔门槛改为"三塔已建后才有升级储备"——即升级储备只对第 4 个不存在的槽位生效，实际上等于**删除升级优先于三塔的排序**，改为"三塔 > 主武器 L2 > 墙券 > 基地券"。
- 保留的底线：不覆盖已有塔（validate.rs:158）、三塔上限、批量交易。

### 4.3 采购预算与 deadline 的正确设计

现有的 intent/deadline 预算器（economy.rs:180–351）方向正确，需要修的是三处执行：

1. **现金与潜在财富分流**：`liquid_gold` 只应用于"是否值得提前走向商店"（已修石头问题）；**所有门槛判定**（`upgrade_reachable`、`third_tower_fallback`、Bomb/Dizzy 的 `gold>=150`）必须改用 `turn.gold`（现金）——潜在财富不是购买力，用它做门槛就是门 B 死锁。
2. **最低收入下限**：每天设定"DUSK 前现金 ≥ X"（建议 X=60：一张药 + 两个修墙包的夜班本钱），把该目标作为 `should_sell` 的强制项：未达下限且背包有货时，卖矿优先于除自愈/封口外的一切。这补上了"卖矿纯靠批量阈值触发"的被动性。
3. **通勤合并**：经济工人的路线改为显式环路（矿 → 小贩 → （有购买力时）商店 → 矿），由状态机驱动而非每回合重算目标；`buyer_flow` 只在该环路经过商店时消费，不再独立拽人。消除三角震荡，等效收入 = 采集回合占比提升。

## 5. 长期未解决问题的根因（六类顽疾逐个剖）

### 5.1 第三塔从未建成（5+ 场）
**根因**：升级优先的储备策略预设了不存在的收入水平；fallback 的触发条件（`upgrade_reachable` 用潜在财富判定）与其目的（升级不可达时补塔）逻辑相反——潜在财富永远"可达"，因为矿在背包里。四道门全部错配（§4.2）。**不是没修过，是每次修都在阈值上打转（#9 加 fallback、#15 放宽到 gold≥125），没人动"升级 vs 三塔"的排序本身。**

### 5.2 任务答案 schema 不符（0/N 贯穿全赛季）
**根因**：schema 的两个权威来源（沙盒任务文件、`errors[].description`）一个没去读、一个读了扔掉（model.rs:336）。`expected_fields` 从占位描述猜字段是方法性错误——占位文本（"请阅读task_X.md，获取任务信息"）里没有任何字段信息，猜对是巧合，猜错是必然（#22 多 status 字段、#23 `{"city"...}`、#15 裸值 vs 包装）。**根因不在 LLM，在反馈环断裂。**

### 5.3 经济冻结（金 5–25）
**根因**：D1 零收入设计 + 单一收入通道 + 潜在财富与现金混用 + 三角通勤 + 任务金币为零，五因叠加（§4.1）。**既往修复全部针对单因**（阈值、专职工人、矿石选择、liquid 剔石头），每修一因，冻结从次弱的一环复发——issue 里自己称之为 "root-cause-migration"。只有当作"系统稳态"整体改造（§4.3 三条）才能终结。

### 5.4 `controller_withdrawn` ≈30 次、塔哑火
**根因**：撤退规则（#20 引入）本身是对的，但它把矛盾从"人死在岗位上"转移成"人活着炮哑了"，因为两个配套条件缺失：① 没有药的经济（撤退者 HP 冻结 20，235 回合无恢复路径，#22）；② 撤退判定不做安全性/替手测试（机器人进内环后撤退无意义，§3.3-D1）。**这是经济问题在夜间的投影**——药 10 金，金 5 冻，一切撤退都是永久退役。

### 5.5 墙环夜间重开、每日 6 格修不回去
**根因**：预算问题已被 `ring_ever_complete`（state.rs:315 + day.rs:122）解决一半（#23 验证修复 18→19），剩下的是**修复速度 < 破坏速度**的结构性问题：单层环无冗余、修墙靠采石（占一个工人全天）、WallFixer 无钱买、杀啃墙者的火力优先级不够（§3.3-D3）、主动道具（眩晕）没有预算位（§3.3-D4）。6 格预算不是瓶颈，钱和火力和人力是。

### 5.6 任务点死亡螺旋（retire 生效但仍 0/8）
**根因迁移链**：死在点上（#3 修）→ 空转接取（#8 修）→ 窗口全拒（#17/#18 修）→ 哨兵占位（#20 修）→ 死点重复进入（#21 修，`retire_dead_task_point` 生效）→ **当前：答案 schema 错 + 不可赢任务照接**。每一环都是真修，但终点线一直是"答案对不对"，而答案对不对取决于 §5.2 的反馈环。链条只剩最后一环，也是信息最全的一环（判题器直接告诉我们哪里错）。

### 5.7 元根因：修复模式本身
六个顽疾共享同一个元根因：**修复以"上一场日志里最刺眼的症状"为靶，而系统的三个子系统（任务/经济/防御）通过金币与先锋时间深度耦合，局部补丁把故障在耦合环路上推来推去。** 次要元根因：修复与实战验证之间存在时间差（#23 用 4de5194 的比赛验证 561640b 之前的码），AGENT_REQUEST 请求三（battle base commit）未落实前，每份 issue 的"修复目标 vs 结论"都在混用版本。本方案 §6 的每一项都要求绑定验证方式，正是针对元根因。

## 7. 与既往修复的冲突说明

1. **与 issue #3 修复（`49db97a`：先建 1–2 塔、留 25–50 金升级储备）及 AUDIT_PLAN P1-3（两塔先升级、第三塔动态决策）冲突。**
   P0-2 主张 D1 直接三塔、删除"升级先于三塔"的排序。理由：该策略的正确性依赖"D1 有收入"的假设，而 D1 零收入是墙环设计（`shared_wall_duty`）的必然结果；连续 5+ 场（#9/#15/#20/#22/#23）实测第三塔永远等不到资金，对手零储备三塔（#20 R1–R4）全部跑赢。AUDIT_PLAN 自己预留的 fallback（"入夜前升级不可达则 25 金补 rocket"）因 `upgrade_reachable` 用潜在财富判定而从未触发（§5.1）——不是策略错，是策略的前提在本赛制不成立。**避免回退的方法**：不恢复"花光 75 金不留药钱"的旧极端——P0-2 保留 D1 黄昏首批卖矿买药的硬目标（P1-4 的现金下限覆盖），且三塔后 `validate.rs` 的防覆盖/三槽上限不动。
2. **与 issue #20 修复（控制器带伤撤退，`night_withdraw`）的张力。**
   P0-5 不是回退撤退，是补上它缺失的两个测试（安全格存在、替手存在）。#20 的抱怨（死在岗位、塔哑 24 回合）与 #22 的抱怨（撤退 35 次、塔哑整夜）是同一权衡的两面；正确的解不是二选一，而是"撤退仅当它有火力代价之外的净收益"。保留：撤退优先级高于召回的次序、Medicine 先于撤退的检查（night.rs:522–535 注释链）。
