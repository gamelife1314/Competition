## 1. 得分失血分析

### 1.1 计分结构（任务书第6章）

- `score1` 任务分：完成 = 奖励 + 5×标准回合/实际回合；部分完成 = 奖励×通过率。**关键口径（接口文档 PlayerTask.timeoutRounds）：任务超时强制结束时，按「之前提交过的通过率最高的答案」结算积分与金币**——提交是累加制的，判错（errorCode 2）不清零已有通过率。
- `score2` 击杀分：小/中/大/BOSS = 1/2/4/10。
- `score3` 生存分：Σ 10×day×存活系数，满 10 天 550；基地被毁当天起归零（D1 毁 = 0，D2 毁 = 10，D3 毁 = 30）。
- 胜负（第7章）：**先被摧毁的一方判负**；都未毁才比积分。—— 生存优先于积分。

### 1.2 三项失血的量化（issue 实证）

**score1（任务）—— 最大失血口，且是「稳定的 0」**

| pk577297 | #21 | 0（8 session：4 错答 + 4 超时） | 240（3 个任务） | **-240** |
| pk576630 | #17 | 0（2 session 超时） | 345（4 个任务） | **-345** |

我方最近一次任务得分是 pk575935（#13，+86）和 pk576068 时代（#14，R18 首个任务 +80 后到 181 分）。**#17 之后的 6 场比赛、40+ 个 session，任务分合计为 0。** 而对手单场任务分 139–345，是我方全场总分的 1.5–6 倍。任务金币（80+/个）同时是对手升级火力的主要财源（#13 对手 R23 用任务奖励 100 金买 WeaponUpgradeVoucher1；#10 对手两个任务各 +80 金）。

**score2（击杀）—— 存活时并不差，但受火力天花板压制**

- pk577297：kill=105（#21）；pk576775：总击杀 175（夜间 143），但 361 回合总伤害仅 4930（每回合 ~14），D4 夜间基地每回合掉血 ~80（#18）——**清怪速度约为失血速度的 1/6**。
- 基地早毁的场次击杀随之归零：pk576630 总分 19（#17）。

**score3（生存）—— 决定胜负的摆动项**

- 基地被毁：pk576630 D1 R110（#17）、pk576068 D1 R110（#14）、pk576234 D1 R105–115（#15）、pk577076 D2 R256（#20）、pk576775 D4 R351（#18）、pk574902 D3 R361（#8）。
- 幸存（胜场）：pk577716 45HP@R256、pk577297 20HP、pk577572、pk576926 75HP、pk576466 35HP。
- **三场 3:0 胜利（#21/#22/#23）全部是「对手基地先被夜间机器人摧毁」赢的，不是积分赢的**：单局积分 -87（#23）、-4（#22）、-313（#21），系列赛却 3:0。机器人同时攻击双方基地（#23 attack_map 证据），对手无墙无夜防即死。一旦遇到能活过 D1 的对手（#17 的奥特曼打怪兽、#11 的汪汪队），按积分判我们就输。

### 1.3 结论：失血排序与最大收益项

1. **score1（任务）是最确定、最大的失血**：每场稳定 -139 ~ -345，且附带每场 -80 ~ -240 金币的机会成本（这些金币正是对手买升级的财源）。把任务从 0 分修到「每场 2 个任务 × ~85 分」，单场积分直接 +170 以上，并把经济从矿业小循环升级为任务奖励大循环。
2. **score3 是胜负的摆动项**：从「D1 毁（0）」到「活过 D2（30）」到「全程（550）」。当前 D1 已能守住（墙环验证有效），失血前沿在 **D2–D3 夜**（#21 墙 17→7、基地 1500→20；#23 墙 19→13、基地 1165→45）。
3. **score2 是火力的函数**：2×L1 塔的理论上限已不够 D2 的 90+ 怪潮（见 §3.1 的算术），火力升级依赖经济，经济依赖任务金币 —— 三项失血在「任务」这一点汇合。

## 2. 任务系统全面重构方案

### 2.1 完整失败链诊断（发现→路径→LLM→格式→提交→成功判定）

| 环节 | 历史根因 | 现状 |
|---|---|---|
| 发现 | 重复进入 cmdRounds=0 的死任务点 | ✅ 已修（#21 `retire_dead_task_point`，#23 验证 4 次退役） |
| 路径 | `cat task_X.md` 猜根目录 | ✅ 已修（prompt 强制 find `/tmp/selfEvolutionTask/`） |
| 执行窗口 | executeCmd 在 LLM 应答回合被判非法 | ✅ 已修（#18/#19：llmResp 回合不执令；#21 后 JUDGER_ERROR 消失） |
| 哨兵答案 | `xxx`/`failed_to_extract` 被当答案提交 | ✅ 已修（#20 `is_failure_answer`，#22 验证 0 哨兵） |
| **LLM 答案构造** | **一锤子脚本盲猜 API/格式** | ❌ **当前主根因**（§2.2） |
| **schema 符合** | **多字段/少字段/包装层错** | ⚠ 部分已修未验证；**校验对象错了**（§2.3） |
| 提交策略 | 把提交当「终局动作」，答错 3 次放弃 | ❌ **策略性错误：与积分口径相反**（§2.4） |
| 成功判定 | 三信号确认（point closed + phase 缺失 + 无错误） | ⚠ 偏保守，但有超时兜底，不是主因 |

### 2.2 主根因 A：一次性脚本规则与「先读后做」的任务形态根本冲突

`task.rs::build_prompt` 规则 4 要求「尽量在一个脚本内完成全部步骤，不要分多轮试探」。但真实任务（issue 实证）是：

- `task_1_beijing` / `task_2_nanjing`（#11/#14/#22/#23）：沙盒内有 `API_DOCS.md`，需要先读文档才知道端点与**鉴权头**。我方 pk576068 因 API 404 失败（#14）；**对手读到 401 后回去读 API_DOCS.md、换对头，成功**（#14）。我方 pk575557 对同类 API 任务连错 5 次（#11）。
- 工程修复类（alpha/beta，#12/#13/#15）：需要先 `cat` 任务与 check 脚本，再修。我方唯一一次成功（pk575935 +86）正是 LLM 在 2 次错误后识别 `^M` 换行问题才过的——**那次成功本身就是「多轮试探」的产物**。

LLM 在看不到文件内容时写出的「一步到位」脚本，只能盲猜端点、字段名与输出格式，于是产出 #22/#23 看到的：值错（"29"）、markdown 标题、多 `status` 字段。**一锤子规则把「探索」污名化为浪费回合，实际盲猜才是浪费回合。** 而重试反馈链（`result_history` 带进下次 prompt）虽然存在，但超时只有 10–15 回合（#18/#19 实测 timeout 2–15），每次 LLM 往返要 2 回合（prompt→llmResp→executeCmd→lastCmdResult 共 4 回合/次尝试），盲猜 2 次就用完了。

**改造方案**：把 prompt 协议改成显式两阶段——
1. **侦察阶段**：若任务文件提到任何未见内容的 API/文档/脚本（`API_DOCS.md`、check 脚本、数据文件），第一个脚本只做 `find + cat` 并原样输出，**禁止**打印 `ANSWER:`。这一步产出的是「任务的真实 schema 与接口契约」。
2. **求解阶段**：带着侦察输出写求解脚本。规则 3 的 `{{参数}}` 占位与规则 6/7 自检保持不变。
侦察脚本本身可缓存为 SOP 的第一步（同类任务侦察结果同构），把后续任务的 LLM 往返再省一轮。

### 2.3 主根因 B：schema 校验在错误的文本上做

`task.rs::expected_fields(description)` 从 `state.task.description`（即 `phaseTask` 原文）提取字段。但 issue 证据显示 `phaseTask` 往往是**泛化文本**：「请阅读task_X.md，获取任务信息」（#11/#12 三次 task_started 均是这句）。真正的输出 schema 在沙盒里的 `task_X.md` 内。于是：

- `expected_fields` 对泛化描述返回 <2 个字段 → `answer_schema_gaps`/`answer_schema_extras` **直接放空**（代码里 `fields.len() < 2 → Vec::new()`），#22 加的两道闸对这类任务形同虚设；
- LLM 看不到强制 schema，自由发挥就发明 `status`/`note` 字段（#22 session 5）或包一层 `{"token": …}`（#15）。

**改造方案**：schema 从任务文件来，不从 phaseTask 来——
1. prompt 要求 LLM 在求解脚本的输出里，先打印一行 `FIELDS: 字段1,字段2`（从 task_X.md 原文摘录的要求字段），再打印 `ANSWER:`；
2. `on_cmd_result` 解析并缓存 `declared_fields`，`HaveAnswer` 的 schema 闸改用「declared_fields ∪ expected_fields(phaseTask)」做 gaps/extras 校验；
3. 无 declared_fields 时退回现有逻辑（保守放空），不产生回归。

### 2.4 主根因 C（最深）：提交策略与积分口径相反 —— 「提交是累加的，不是终局」

接口文档写明：**超时强制结束时按「此前提交过的最高通过率」结算**。这条口径推翻三个现有设计的前提：

1. **答错不亏**。errorCode 2 =「不正确或不完全正确」，但通过率已入账（保留最高值）。连错 3 次放弃（`MAX_WRONG_ANSWERS=3`）是把「还能继续提高通过率」的 session 提前杀掉。对手的做法（#10）：8 次 `MissingNamedInput` 拒绝后仍每任务重试 4 次直至成功。
2. **越早提交越赚**。当前流程把提交放在链路末端，还要先过 schema 闸（`SCHEMA_GRACE=4` 内不提交）。正确做法是：**第一次 `HaveAnswer` 立即提交**（入账当前通过率），schema 反馈照样进入下次 replan，有更好答案再提交覆盖。提交动作不结束任务（任务书 5.3 的四种结束方式不含提交），成本只是一回合动作。
3. **超时不等于失败**。分析工作流一直把 `reason=timeout` 统计为失败，但只要提交过答案，超时照样结算通过率。真正的零分 session 只有两类：**从未提交**（cmdRounds=0、LLM 全程没产出 ANSWER、哨兵/markdown 被拦后重规划到超时）和提交了 0% 通过率答案。消灭「从未提交」比提高单答案质量收益更大——`partial_answer` 在 `rounds_left<=2` 的兜底已是对的方向，但它只吃带 `ANSWER:` 标记的历史；应扩展为：只要有任何**结构化部分答案**（JSON 字段并集、或脚本明确算出的标量）就在死线前提交。**注意**：既往红线「探索性输出/元描述答案绝不可提交」必须保留——兜底只提交「有证据的结构化值」，不提交 find/ls 原文。

### 2.5 辅助根因 D：SOP 缓存与「快速放弃」互相打架

`finish_task` 现在对「产出过答案的脚本」都会缓存（`sop_cmd`），这是对的；但 `observe()` 在 errorCode 2 时调 `drop_sop_for(task_type)` **整类删除**。一个脚本答错通常是**值**错（API 参数、城市名），不是**流程**错；删缓存使下一个同类任务退回 LLM 往返，在 10 回合超时里大概率又是零提交。对手（#10）的行为是「保留流程、修正输入」。

**改造方案**：errorCode 2 时不删 SOP，给该 entry 记 `rejections += 1` 并附上判错反馈；复用时若 fingerprint 匹配仍直接跑（省 4 回合），但把「上次此脚本被判错，注意修正参数」注入后续 replan prompt；同一 entry 连续 2 次判错才淘汰。这保留 #15「快速放弃 session」的本意（放弃的是 session，不是经验）。

### 2.6 对手成功模式（证据汇总）

- #10（pk575412 对手）：接任务 → 被拒（MissingNamedInput）→ **调整 known_inputs 重试** → R11→R27、R30→R47 各完成一个（+80 分 +80 金）。
- #13（我方 pk575935）：LLM 2 次错误后识别 `^M` 问题 → +86。**多轮反馈是成功的必要条件**。
- #14（对手）：401 → 读 API_DOCS.md → 换鉴权 → 成功。**读文档是 API 任务的必要条件**。
- #15（对手）：「任务失败快速放弃，把开拓者投入防御」——单 session 及时止损，但**不放弃任务线整体**。

结论：成功 = 侦察（读文件/读文档）→ 求解 → 提交入账 → 带反馈迭代。我方当前缺「侦察显式化」「schema 来自任务文件」「提交累加观」三块。

## 3. 生存与防御策略升级

### 3.1 核心算术：2×L1 塔在数学上就守不住 D1 夜以后

任务书数值：小机器人 40HP/5攻，D1 夜 70 个（#14 实测）；D2 夜 90+（#8）。

- D1 夜波次总 HP = 70 × 40 = **2800**。我方 gatling L1（10/轮）+ railgun L1（10/轮）= **20 伤害/轮**；60 回合全打满 = 1200，**连 D1 波次的一半都清不掉**。实测吻合：D1 夜墙吸伤 2750–3260（#19/#21），靠 20 墙 20000 HP 硬扛才零基地损伤。
- D2 夜 90+ 个且混中/大型，需要的清怪能力大约翻倍；而我方火力停在 20/轮（#18 实测每回合 ~14 伤害 vs 基地每轮 ~80 失血）。
- 结论：**第三塔 + L2 升级不是优化项，是 D2 起生存的数学必要条件**。3 塔（含 rocket 溅射）+ 主武器 L2 ≈ 60–90 伤害/轮，才能把「清怪曲线」抬到「失血曲线」之上。这解释了所有 D2–D3 夜死亡（#8/#18/#20/#21/#23）：不是墙不够，是火力掉队后墙被纯消耗。

### 3.2 基地反复被拆的防御链诊断（当前状态）

1. **D1 白天**：墙环闭合（✅ 已验证，R56–R60 seal，13–20 墙）。2 塔到位（gatling+railgun）。第三塔缺席（见 §5.1）。
2. **D1 夜**：墙吸伤，塔清怪不足，残余怪磨墙；控制器被打到 <30% 后 `night_withdraw` 撤退 → 塔哑火 → 更多怪活到天亮。**撤回后无治疗路径，HP 冻结 235 回合**（#22 实测 20012；`561640b` 加了买药 errand，未验证）。
3. **D2 白天**：破环修复预算已修（#21 `ring_ever_complete`→20/天，验证 R201 修 18→19）；但**墙 HP 不恢复**（WallFixer 无钱买，#16 的老问题在 #21/#23 仍在：墙数回来了，HP 池持续下降），且**门重封依赖碰巧有石头**（§5.5 的结构性 bug）。
4. **D2 夜**：90+ 怪潮 vs 2×L1 塔 + 半血墙 + 带伤控制器 → 破环 → 基地 1500→20–45（#21/#23 完全一致的模式）。

链条归纳：**火力不足（2 塔 L1）→ 怪活到天亮 → 墙纯消耗（HP 无修复）→ 控制器带伤哑火 → 火力进一步下降 → D2/D3 夜破环**。墙只是缓冲，火力与治疗才是解；而火力（第三塔 25 金、L2 券 100 金）与治疗（Medicine/WallFixer 10 金）全部卡在经济上（§4）。

### 3.3 更智能的防御策略（非参数微调）

1. **按「清怪算术」排资金目标**（替代固定优先级）：每晚开始前估算 `wave_hp（按当日怪数×HP）` 与 `我方 60 回合理论输出`，缺口>0 时，下一白天资金目标强制为「补火力」（第三塔/升级券），缺口≤0 才允许基地升级与骚扰消费。把 `may_build_weapon` 从「金币门槛」改成「清怪缺口驱动」。
2. **基地升级券应进入生存预算**（当前从未购买，#23）：StationUpgradeVoucher1 = 100 金换 +1500 HP（≈ 一整个 D2 夜的基地承伤），与 WeaponUpgradeVoucher1（100 金 ≈ 单塔 DPS 翻倍）应按 §3.1 的缺口模型 A/B 排序。现有 `CG_TUNE_*` 拨盘可直接做实验，不需改代码结构。
3. **墙 HP 池管理**：WallFixer 10 金 = 单墙回满（1000–3000 HP），是全游戏最便宜的 HP。规则：D2 起每天备 2–4 个；夜间 spare 角色在安全半径内修复「开口旁的最弱墙」（`repair_target` 已有此排序，缺的是货）。墙升级券（20 金 = +500 上限**且回满**，任务书：升级后恢复满血）应优先用在「开口旁」的墙上——一次购买同时完成「修复 + 加固」。
4. **控制器续航**：readiness 采购从「全队 1–2 瓶」改为「每个控制器 1 瓶」（30 金/夜），配合已验证的夜间 70% 阈值喝药规则，`night_withdraw` 将很少触发；撤退振荡加滞回（撤退中的控制器 N 回合内不配枪，见 §5.4）。
5. **以「比对手活得久」为合法取胜路径**：三场连胜都是机器人拆了对面的基地。防御优先是被验证的胜策略；但要对「能活下来的对手」准备 B 计划——那只能靠任务分（§2）与火箭 L3 全图压制（`station_killable` 已有）。

## 4. 经济与建造死锁

### 4.1 金币为什么长期冻结（根因链，按贡献排序）

1. **任务金币 = 0（最大头）**：对手每个任务 +80 金，是我方矿业日收入（一名工人一天约 40 矿 × 2–5 金，扣通勤后净入 <100）的同量级甚至更高。任务线死掉，经济就只剩矿业小循环。#17 已指出这个恶性循环：任务失败 → 无金币 → 无钱建墙/升级 → 夜防崩 → 空转。
2. **`liquid_gold` 把 stone 当现金**（`561640b` 已修，未验证）：stone 是墙料、`sell_command` 拒卖，却被计入「购买力」→ `upgrade_reachable` 恒真 → 第三塔 fallback 永不触发；同时 `buyer_must_preposition` 让唯一经济工揣着卖不掉的石头驻守商店 44 回合/天（#22 实测：全场 1 次 sell）。
3. **买家行程压过卖货**（`561640b` 已修，未验证）：buyer 分店在 sell 分店之前，揣着没卖的矿去商店，买不了（店只收金），矿又背回矿点。
4. **残余风险（修复后仍在的结构问题）**：
   - **买家与经济工是同一个角色**（`buyer_id = workers.last() = economy_id`）：矿点→小贩→商店三点通勤，一次采购周期 30–40 回合，一天最多 1–2 次购买；采购行程直接吃掉采矿回合。
   - **第三塔 fallback 的 25 金无人守护**：两塔后 `tower_build_reserve = 0`，消耗品（Medicine/WallFixer）与券的购买 floor=0，可随时把金币花到 <25；fallback 又要求 `gold >= 25` 才建——小额采购可以无限期把金币压在 5–24 区间（#22/#23 实测冻结在 5/25 完全吻合）。
   - **墙料与收入的矿石争背包**：`sellable_ores` 的设计是对的，但 D2+ 门机制（§5.5）会让经济工被困环内/环外，通勤进一步恶化。

### 4.2 deadline 预算器的评价与修正

`intent_list`/`shopping_list`/`buyer_must_preposition` 的框架（AUDIT P1）方向正确，缺两点：

1. **「第三塔」不在 intent_list 里**：它不是商店商品，是 build 行为，所以 deadline 体系管不到它。应把「D1 夜前建成第三塔」建模为一个资金目标：在 fallback 窗口（day_round ≥ 35）且升级不可达时，**reserve 提为 25**，消耗品购买不得击穿它。
2. **升级可达性要按「清怪缺口」而非「金币可达」判断**：`upgrade_reachable` 现在是 liquid ≥ 100 的纯资金判断；应叠加 §3.1 的火力缺口——缺口大时，100 金先买武器券还是 25 金先建第三塔，答案可能是后者（25 金立刻 +1 操控位 +1 火力通道，100 金只强化已有通道）。

## 5. 长期未解决问题的根因（六类顽疾逐一）

### 5.1 第三塔从未建成（5+ 场）

- **表层**：`tower_plan mayBuild=false, reserve=0, gold=5`（#23）。
- **中层**：`liquid_gold` 含 stone → `upgrade_reachable` 恒真 → `third_tower_fallback` 永不触发（`561640b` 已修，未验证）。
- **深层（修完仍会漏）**：fallback 条件 `gold >= 25` 与「消耗品/券 floor=0 可花到 0」矛盾——**没有任何机制为第三塔守护 25 金**；且 fallback 只在 `in_day_round >= 35` 才开，若此时经济工正在商店/小贩往返路上（30–40 回合采购周期），窗口直接错过。
- **真正的修复**：① fallback 窗口临近且升级不可达时，build_reserve 提为 25（守护资金）；② 把「D1 建成第三塔」设为显式资金目标进入 deadline 体系；③ 用 §3.1 清怪缺口替代纯金币门槛。保留硬性约束：建塔顺序 gatling→railgun→rocket、不覆盖已有塔、三塔上限。

### 5.2 任务答案 schema 不符（北京任务 `{"city"…}` 被拒）

- **表层**：LLM 答案格式/值错（#22/#23）。
- **中层**：多字段（`status`）、包装层（`{"token":…}`）、markdown 标题 —— `561640b` 及之前各修了一层。
- **深层**：**判分的 schema 在沙盒任务文件里，不在 `phaseTask` 里**。`expected_fields` 对「请阅读task_X.md」这类泛化描述提取不到 2 个字段，所有 schema 闸直接放空（§2.3）；LLM 又在「一锤子」规则下盲猜 API 契约（§2.2）。
- **真正的修复**：FIELDS 回显 + 侦察显式化 + 提交累加观（§2.2–2.4）。

### 5.3 经济冻结（金币 5–25，买不到 100 金券）

- 见 §4.1。要点：`561640b` 修的是「把石头当钱」和「先买后卖」两个血栓，但**任务金币缺位 + 买家/经济工同人 + 第三塔资金无人守护**三个结构性问题仍在。验证方式：下一场对战日志里 `sell`/`buy` 事件数与金币曲线（健康线：D1 ≥ 2 sell，D2 能见到 100+ 峰值）。

### 5.4 `controller_withdrawn` ×30、塔哑火

- **表层**：撤退逻辑工作（控制器不死在岗位上，#20 目标达成），但暴露「撤退后无恢复」。
- **中层**：`561640b` —— 配对避开撤退者、缓存键纳入撤退集合、重伤白天买药 errand。未验证。
- **深层**：① 伤口只有 Medicine 能愈，而药在经济上 —— 又是经济问题；② **振荡风险仍在**：全部控制器带伤时，配对 fallback 仍会把枪分给伤员 → 走向塔 → 进入威胁半径 → 再撤退，每轮损耗一个走位回合，塔持续哑火。需要滞回：`withdrawing` 过的控制器在「HP 恢复 或 连续 N 回合无威胁」前不参与配对（`night_pair_withdrawing` 已为此留了状态位）；③ readiness 采购 1–2 瓶不够 3 个控制器分（§3.3-4）。

### 5.5 墙环夜间重新开口、6 格预算修不回来

- **修复预算**已修（#21，`ring_ever_complete` → 20/天，验证）。
- **真正的结构 bug（本次新发现，未修）**：**门的重封依赖「黄昏时碰巧有工人带石头」**。`open_door`（D2+ 每天早上切门）把门记入 `door_cells`；`wall_gaps` 在白天过滤掉门 → `stone_demand`（= wall_gaps.len）**不含门** → 若环除门之外完好，全天 `want_stone=false`，没人采石；黄昏 `wall_gate_sealed` 后 step 3 的封门分支要求 `role.count_item(STONE) > 0` —— 没人有石头，**门整夜敞开**，机器人长驱直入。这就是「墙环夜间重新开口」的机制性来源（与机器人打洞的损耗叠加）。
- **修复**：门被切开的当天起，`stone_demand += door_cells.len()`（门计入采石需求，但黄昏前仍不作为 build 目标），并指定非经济工在黄昏前为「封门」备 1 块石头；回归测试：D2 早上切门、黄昏前环必须重新闭合。
- 夜间被怪打掉的墙无法夜间重建（规则限定白天 build），夜间只能 WallFixer 修复存活墙 —— 回到经济问题（§3.3-3）。

### 5.6 任务点死亡螺旋

- 「重复访问死点」已修（#21 验证 4 次退役）。根因已迁移到「LLM 答案错」（#23 原文确认），见 §2。注意把工作流的统计口径一并修正：`reason=timeout` 不等于 0 分，「0 提交」才是 0 分（§2.4-3）；分析 workflow 应统计 `submittedRound` 非空的 session 比例作为任务健康度第一指标。

## 附：一页纸结论

1. **最大问题是任务 0 分**（每场 -139~-345，且掐断任务金币财源）。最深根因不是某个 bug，而是**策略与积分口径相反**：提交是累加的（超时按历史最高通过率结算），我们却把它当终局动作；schema 在沙盒任务文件里，我们却在泛化的 phaseTask 上校验；API 任务需要先读文档，我们却要求一锤子脚本。→ P0-1/P0-2。
